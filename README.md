# 云顶山景区观光车排队上车与站点调度平台

把**票务、排队、车辆、站点、退票**联动起来的全栈演示系统：游客、站点工作人员、司机、调度中心、客服/主管、财务六类角色围绕**同一张车票 / 同一班车**协同处理，目标是减少热门站点拥堵，并在异常（满载跳站、误乘反方向、老人优先争议、车辆故障、司机交班延误、**暴雨临时停运**、退票争议）发生时自动联动所有相关方。

**本次新增：暴雨临时停运完整闭环**——橙色及以上预警一键停运后，平台**分别锁定在途车辆、站点排队、未检票订单**三类车票；游客可对每张票三选一（**改乘 / 延期 / 退票**）；调度中心登记**司机收车**与**车辆充电安排**；财务**按票种生成改期/退票金额**，经客服统一口径批量核准、**财务确认退票 → 出账 → 退票单同步归档**。

- 后端：NestJS 10 + TypeORM（**默认 SQLite，零外部依赖；可通过环境变量切换 MySQL**）
- 前端：React 18 + Vite + Ant Design 5
- 启动后自动建表并写入演示种子数据（2 条线路 / 10 个站点 / 6 辆车 / 4 名司机 / 6 张在途票与排队）

## 一、本地启动

### 方式 A：Docker 一键启动（推荐）

需要 Docker 20.10+ 与 Docker Compose v2。仓库根目录执行：

```bash
docker compose up --build
```

- 前端（游客/各工作台）：<http://localhost:8080>
- 后端 API：<http://localhost:3001/api>
- SQLite 数据持久化在 named volume `server-data`（容器内 `/app/data/app.sqlite`），重建容器不丢数据；`docker compose down -v` 可彻底重置。

### 方式 B：两个终端本地开发

需要 Node.js ≥ 18（开发环境为 Node 22）。

#### 1. 启动后端（端口 3001）

```bash
cd server
npm install
npm start
# 看到 [scenic-shuttle] API listening on http://localhost:3001/api 即成功
# 首次启动自动建表 + 写入种子数据
```

#### 2. 启动前端（端口 5173）

```bash
cd web
npm install
npm run dev
```

浏览器打开 <http://localhost:5173> ，左侧切换 7 个工作台：**游客 / 站点工作人员 / 司机 / 调度中心 / 客服·主管 / 财务 / 运营复盘**。

> 如遇 npm 缓存权限错误（`EACCES ~/.npm`），可加参数：`npm install --cache /tmp/npm-cache`。
> ts-node 首次冷启动编译较慢（低配置机器约 1 分钟），属正常现象。

### 重置演示数据

停止后端后删除 SQLite 文件再启动即可：

```bash
rm -f server/data/app.sqlite
cd server && npm start
```

## 三、暴雨临时停运：业务闭环（本次重点）

```
橙色预警(level≥3) → 调度一键停运
        │  锁定三类：①在途车上已检票 ②站点排队（保留顺位）③未检票有效订单
        ├─ 在途车辆 V02 → 状态「待收车」，停止派班/入队/检票
        ├─ 调度登记：司机收车（停靠点/在车人数）→ 车辆充电安排（桩位/目标电量/开始/完成）
        ├─ 全线广播 + 客服端同步「统一口径」
        ├─ 游客逐张三选一：
        │     改乘 → 免手续费、原票款结转、恢复后优先接驳/首班、排队顺位保留
        │     延期 → 免手续费、票款结转至改期日、优先/轮椅资格保留
        │     退票 → 按票种全额生成退票单（单程¥20/人 环线¥35/人 亲子¥30/人 无障碍¥20/人）
        ├─ 客服：逐笔核准 或 对某停运单「批量核准」暴雨退票（金额同步财务）
        ├─ 财务：确认退票（渠道/复核备注）→ 出账退款 → 退票单同步归档（AR 单号）
        │        改乘/延期单为票款结转（不流出），结转后归档
        └─ 预警解除 → 调度恢复运营：未退票游客解锁、排队顺位恢复、派班恢复
```

| 环节 | 平台行为 |
| --- | --- |
| 锁定在途车辆 | 在运/上客/计划班全部转「停运」；车辆置 `待收车`，不自动复位，等待登记司机收车 |
| 锁定站点排队 | 队列状态转 `停运锁定`、停止叫号检票，顺位保留；站务看板单列“锁定队列” |
| 锁定未检票订单 | 当日有效、未入队的票按线路锁定，停运期间不能排队检票或走普通退票 |
| 游客三选一 | 每张票一次选择机会；改乘/延期生成结转单（免手续费），退票生成全额退票单 |
| 司机收车 | 登记就近停靠点、收车时在车人数；登记后车辆转待命、司机收车，才可安排充电 |
| 车辆充电安排 | 指定桩位/目标电量，支持「待充电→充电中→已完成」，完成后电量补满转待命 |
| 客服同步口径 | 工作台顶部展示停运单、三类待处理数、选项进度与统一答复口径，可一键批量核准 |
| 财务按票种 | 金额后端按票种×同行人数生成；财务确认→出账→归档三步留痕，报表按“暴雨停运”归责 |

### 手工点点看（推荐验证路径）

1. **调度中心 → 天气与道路管制**：把预警改成等级 **3（暴雨橙色）**、降雨 45mm/h，点「更新天气」→ 出现红色「一键临时停运」。
2. 点击**一键临时停运**，记下停运单号（`SS…`），切到新页签 **「暴雨停运处置」**：
   - 看到在途 1 / 排队 5 / 未检票若干、待收车车辆 **V02/陈志强**；
   - 点「**登记司机收车**」（停靠点：百花园避雨点、在车人数 2）→ 待收车清零；
   - 「**新增充电安排**」选 V02、桩位 A区3号桩、目标 100% → 开始充电 → 充电完成（电量补满）。
3. **游客页**：分别查询下列车票，在红色停运卡片上做选择：
   - `T20260925-005`（在途车上）→ **退票**，看到按单程票 2 人生成 ¥40.00；
   - `T20260925-001`（排队）→ **改乘**，¥0 手续费、票款结转、顺位保留；
   - `T20260925-002`（亲子 3 人排队）→ **延期**，选改期日，结转 ¥90.00；
   - `T20260925-004`（环线 4 人）→ **退票** ¥140.00；
   - 再买一张**未入队**的新票也会出现在“未检票”类，可三选一。
4. **站务页（东门枢纽）**：顶部红色停运提示，入队按钮禁用；下方「暴雨停运·锁定队列」实时显示每位游客的选择。
5. **客服·主管页**：顶部「暴雨停运统一口径」展示三类待处理、金额汇总与口径全文；点「**批量核准暴雨退票**」。
6. **财务页**：退票单依次经过 ①**退票确认**（渠道/备注）→ ②**出账** → ③**同步归档**（生成 `AR…` 归档号）；「改乘/延期结转」页签把结转单归档；全部单据页签可查类型（退票/改乘/延期）、退款、结转票款与归档号。
7. 回**调度中心**点「**恢复运营**」（或停运处置页内同按钮），再到天气页把预警降回 0；用 V01+王建国（先完成安检）派班恢复成功；查 `T…-001` 已解锁可继续排队，被退款车票保持「已退款」。
8. **运营复盘页**：KPI 与“退票成本按责任归类”中可见「暴雨停运」退款总额与归档数。

## 四、其他核心业务与异常联动

| 场景 | 平台行为 |
| --- | --- |
| 购票 | 记录入园时间、起终点站、同行人数、婴儿车/老人/儿童、轮椅需求、预计游览路线；无障碍/老人票自动进入**优先组** |
| 站点排队 | 平板看板：排队人数、已检票数、车辆位置、座位余量、轮椅位、天气、道路管制；扫码入队自动校验始发站 |
| 检票 | 一键叫号按「优先组优先 + 同组 FIFO」；自动校验**方向**与座位/轮椅位 |
| 热门站排队过长 | 排队超站台容量 1.2 倍自动生成 `long_queue` 事件并推送调度加车建议 |
| 满载跳站 | 车辆 GPS 到站（电子围栏）发现余座为 0：自动登记跳站、站台游客转回排队、通知调度加车并记录事件 |
| 误上反方向 | 检票口方向不符自动拦截；游客坚持可「强制放行」，事件同步调度安排返程衔接 |
| 老人优先争议 | 站务一键上报 `priority_dispute`，客服工作台接单并可闭环 |
| 车辆故障 | 司机上报 → 车辆转故障、在运班停运、调度派备车、游客无责退票，事件串联票/车/班 |
| 司机交班延误 | 上报后其计划班自动变「延误」并禁止再派班，看板与调度建议同步提示 |
| 退票 | 游客/站务发起 → 生成退票单+事件 → 客服核准/驳回；争议一键**升级客服主管**终局裁决 → 财务确认出账 → 归档；每一步都写在车票时间线上 |
| 团队包车 | 申请→调度配车（校验座位/轮椅位）→车辆预留→开始用车→完单释放 |
| 无障碍 | 无障碍车辆标识、轮椅位库存、轮椅位检票占用、包车轮椅位校验 |
| 司机安全检查 | 发车前 6 项检查；任一不合格车辆自动转维保且派班被阻断 |
| 站点广播 / 限流 | 本站或全线广播；热门景点可设每小时限流人数；停运自动播发全线广播 |
| 电子围栏 | 车辆进/出站自动记录，驱动满载跳站判定与车辆位置更新 |
| 派班校验 | 电量<20%、充电/维保/故障/待收车、包车预留、司机未签到/休息/交班延误/超时未休/达工时上限、安检未过、道路封闭、**暴雨预警与停运单生效**——任一不满足即阻断并一次性返回全部原因 |
| 运营复盘 | 站点等待（平均/最长/被跳组数）、车辆利用率（上座率/里程/电量）、投诉原因分布、退票成本按责任归类（含暴雨退款/归档数）、KPI 总览 |

## 五、切换 MySQL（可选）

默认 SQLite 零配置运行。如需使用 MySQL（8.x），先建库：

```sql
CREATE DATABASE scenic_shuttle DEFAULT CHARACTER SET utf8mb4;
```

然后用环境变量启动后端（`synchronize: true` 会自动建表）：

```bash
cd server
DB_TYPE=mysql DB_HOST=127.0.0.1 DB_PORT=3306 DB_USER=root DB_PASSWORD=root DB_NAME=scenic_shuttle \
  npm start
```

Docker Compose 方式可参考 `docker-compose.yml` 文末注释中的 mysql 服务段。
